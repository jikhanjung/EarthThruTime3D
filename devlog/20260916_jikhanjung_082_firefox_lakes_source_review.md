검토 기준: #47 `a336d25`, #48 `7ff6992`. 사용자 요청은 검토이며 두 PR을 수정·병합하지 않았다.

## #48 — 배포 전 수정 필요

### P1: 캐시된 단일 채널 PNG와 새 호수 셰이더가 호환되지 않음

`static/core/globe.js` 1310–1315는 `.rg`의 green을 호수로 읽는다. 하지만 기존 PNG는
L 모드여서 디코딩하면 R=G=B다. 실제 현재 필드의 최대 R/G가 모두 239인 것을 확인했다.
`core/globe.py` 975·991·1007의 `private, max-age=3600`과 동일 URL이 유지되므로,
서버 자료를 모두 RGB로 바꿔도 기존 사용자는 최대 한 시간 이전 텍스처를 사용할 수 있다.
하천이 호수처럼 표시되는 회귀가 생긴다. 파일 해시/자료 버전으로 URL을 바꾸거나,
명시적인 자료 형식을 전달해 이전 형식을 안전하게 처리해야 한다.

### P1: RGB 전환 전제조건을 패커가 검사하지 않음

PR은 모든 하천 PNG를 RGB로 재생성해야 한다고 설명하지만 `deploy/pack_data.py` 147–152는
존재하는 파일을 복사할 뿐 채널·자료 형식을 검사하지 않는다. 실제 현재 L 모드 150장도
그 패커로 0.14.1 묶음과 이미지 검사를 통과했다. 새 셰이더 배포에서도 이전 자료가 조용히
통과할 수 있다. 배포 전 RGB/스키마 검증을 필수화하고, 구형 입력으로 패킹이 실패하는지
검사할 필요가 있다. 기존 일반·저수위 자료의 green을 0으로 만드는 변환과 빙기 필드
재생성도 릴리스 작업에 포함해야 한다.

PR의 수치 테스트 10개는 분리 로딩해 실행했고 모두 통과했다. 실제 RGB 전체 시리즈는
이 검토에서 생성하지 않았다. 두 문제는 수치 라우팅 결과와 별개의 배포 호환성 문제다.

## #47 — 실행 환경과 실패 처리 보완

### P2: 기본 실행 경로가 macOS로 고정됨

`tests/firefox-browser.mjs` 15–20이 항상 `/Applications/Firefox.app/Contents/MacOS/firefox`를
기본값으로 사용한다. PR 설명의 Linux `firefox` fallback이 실제 코드에는 없다.
Linux에서 안내된 기본 명령을 실행하면 `spawn ... ENOENT`로 실패하며 spawn error 핸들러도
없어서 예외가 정리 구간을 거치지 않는다. 플랫폼별 기본값과 spawn 오류/프로필 정리를 보완해야 한다.

추가 확인: FIREFOX_BIN을 설치된 Firefox 146.0.1로 지정하면 BiDi 연결은 성공했으나
headless 모드의 WebGL2 생성이 `AllowWebgl2:false`로 거절돼 초기 화면 대기 30초 뒤 실패했다.
이것만으로 macOS의 검증 결과를 부정하지 않는다. 해당 Linux 환경에 필요한 실행 조건을
문서화하고, 대기 시간 초과 시 수집한 console/network 오류를 같이 출력하면 원인 파악이 쉬워진다.
현재는 최종 오류 검사가 실행되기 전에 timeout이 발생하여 일반 메시지만 나온다.

또한 `send()`(49–53)는 응답 제한 시간과 socket 종료 시 pending Promise 거부가 없다.
연결 후 브라우저/transport가 멈추면 `until`의 30초 제한에도 불구하고 await 단계에서
무한 대기할 수 있다. transport 종료·명령 제한 시간 처리를 추가하는 것이 좋다.

## #50 — 재현 확인

최신 API JSON을 `/tmp`에 내려받고 같은 `verify()`로 검사했다. 원본 ZIP은 통과하고
metadata는 실패했다. 새 JSON도 12,936 bytes이며 SHA-256은
`1d145319613fa04985433f05f9f216651d43b0aab4741a2e17977a5b0230da27`이다.
기존에 고정한 로컬 JSON과 비교했을 때 다른 최상위 키는 `stats`뿐이었다.
`metadata.license.id=cc-by-4.0`, `metadata.version=3.0`은 같다.

`scripts/geodynamics.py`의 `source()`는 모든 asset을 필수 검증하므로, 변하는 API
레코드 때문에 두 자료 빌더가 모두 막힌다. 이미 생성된 운영 자료를 서빙하거나 현재처럼
그 자료를 패킹하는 경로는 영향을 받지 않는다. 이슈의 새 환경 재생성 문제는 유효하다.

권장 최소 수정은 OPT1 manifest의 mutable metadata 항목을 필수 assets에서 빼고,
license evidence에 record URL·조회 날짜·확인한 라이선스 값을 기록하는 것이다.
ZIP의 고정 크기·SHA-256 검증은 유지한다. 선택적 JSON 보관은 빌드 성공 조건에서 분리한다.
모든 source의 검증을 느슨하게 바꾸거나 API 해시만 다시 고정하면 안 된다.
회귀 검증은 metadata 변경/부재에도 검증된 ZIP으로 진행하고, ZIP 변경은 계속 거부하는지 확인한다.
실제 코드 수정은 아직 하지 않았다.
